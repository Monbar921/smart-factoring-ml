# Данные и покупатели для прогона цепочки (SMF-35)

Здесь тестовый набор данных для загрузчика и пул реальных покупателей, из которого он собран. Клиенты, договоры, УПД и платежи синтетические (клиенты «Клиент NNNN», ИНН клиентов с префиксом `00`). Покупатели — реальные ИНН, их PD посчитана моделью PD на отчётности за 2024 год.

## Что внутри

| Файл или папка | Что это |
| --- | --- |
| `delivery/` | Тестовый набор: пять партий `batch_01` … `batch_05` и `index.json` со списком партий. Подробности ниже |
| `Loader_Setup_Instruction.md` | Короткая инструкция, как загрузчику брать партии (формат файлов, три подводных камня) |
| `buyers_pool.csv` | Пул из 1 500 реальных ИНН: пять блоков по 300, блок — покупатели одной партии из 100 клиентов |
| `buyers_status.csv` | Статус каждого покупателя на дату снимка: ЕГРЮЛ и признак банкротства по ЕФРСБ |
| `buyers_to_verify.csv` | 1 059 ИНН, у которых статус пока подтверждён только по ЕГРЮЛ, ЕФРСБ по ним ещё не проверяли |
| `buyers_methodology.md` | Как пул собран: квоты, целевые доли, отличия от ТЗ |
| `pool_report.json` | Сводные числа по пулу |
| `10_universe.py`, `11_build_pool.py` | Скрипты сборки пула. Справочные: пути в них записаны под среду автора, как есть они не запустятся |

## Тестовый набор (`delivery/`)

В партии 100 клиентов, около 300 покупателей этих клиентов, около 22 тыс. УПД и около 24 тыс. платежей за 33 месяца до `D_end`. Партия самодостаточна: все ссылки внутри неё ведут на её же файлы. Партии между собой не пересекаются, идентификаторы сквозные, поэтому грузить можно одну партию или несколько, в любом порядке. Повторная загрузка партии с тем же `batch_id` заменяет её целиком.

Файлы в каждой партии (`batch_NN/`):

| Файл | Что это |
| --- | --- |
| `clients.csv`, `contracts.csv`, `upd.csv`, `payments.csv` | Клиенты, договоры, УПД, платежи |
| `buyers.csv`, `buyers_status.csv` | Покупатели партии и их статусы на `D_end` |
| `delay_scores.csv` | Эталонные оценки модели задержки на `D_end` для открытых УПД категорий 1–4 (около 1 200 строк): `p_7`, `p_14`, `p_30`, `p_90`, `expected_days`, `status`, `model_version`. Продукт считает эти оценки сам функцией `score_delay`, файл нужен только для сверки. Для статуса `no_history` вероятности пусты |
| `manifest.json` | Паспорт партии: `D_end`, версии моделей, число строк и контрольные суммы файлов |

Формат: CSV, UTF-8 без BOM, запятая, даты `ГГГГ-ММ-ДД`, пустое значение — пустая ячейка. ИНН читать как строку. Полное описание полей — в документе «Контракт данных» (версия 1.0).

Скрытой «правды» (настоящих дат оплат и вероятностей генератора) здесь нет. Она нужна только для проверки данных и в загрузчик не идёт.

## Поля `buyers_pool.csv`

`buyer_inn`, `block` (1–5), `category` (`обычный`, `мало_данных`, `стоп_фактор`, `нет_данных`), `sub_category`, `stop_type`, `snapshot_date`, `okved_section`, `region`, `age_years`, `revenue_mln`, `abs_liquidity`, `current_liquidity`, `payables_days`, `report_year`, `pd`, `risk_level`, `in_buyers_csv`, `buyer_name`.

ИНН читать как строку: ведущие нули значимы. У покупателей «мало данных» PD и уровень пусты.

## Что учесть

1. Дата `D_end` и снимка статусов 30.12.2025 предварительная, её ещё подтверждаем.
2. `buyer_name` пока пустое: названий компаний у нас нет.
3. Статусы собраны из меток когорты 2023. Пока `buyers_to_verify.csv` не проверен в ЕФРСБ, статус «действует, банкротства нет» для этих ИНН предварительный.
4. У трёх покупателей каждой партии нет строки в `buyers.csv` (нет данных). Они есть только в договорах и УПД, и загрузка на них падать не должна.
5. Платёжная дисциплина в данных синтетическая: метрики на этих данных не говорят о качестве модели на реальных оплатах.
