# Модель задержки оплаты по УПД (delay-1.0)

Для открытого УПД, срок оплаты которого ещё не наступил, на дату `t` модель даёт вероятности задержки больше 7, 14, 30 и 90 дней (`p_7`, `p_14`, `p_30`, `p_90`) и ожидаемые дни задержки (`expected_days`). Внутри четыре бустинга LightGBM, калибровка Платта, вероятности упорядочены: `p_7 ≥ p_14 ≥ p_30 ≥ p_90`. Обучена на синтетических данных (генератор gen-1.0). Метрики и причины невыполненных пунктов ТЗ — в `Delay_Model_Report.md`.

## Что нужно для запуска

Пять файлов в одной папке: `delay_model_1_0.pkl`, `score_delay.py`, `dl_common.py`, `dl_model.py`, `alloc.py`. Имена модулей менять нельзя: в пикле лежат ссылки на классы из `dl_model.py`. Остальное (`dl_train.py`, `dl_eval.py`, `dl_dataset.py`, `dl_cv.py`, `make_*.py`, ноутбук, `art/`) нужно только для обучения и проверки.

Зависимости: `numpy`, `pandas`, `lightgbm`. Обучали на Python 3.13, numpy 2.5.3, pandas 3.0.5, lightgbm 4.7.0. Проверка загрузки: `python -c "import score_delay; score_delay.get_model()"`.

## Как вызвать по CSV-партии

```python
from score_delay import score_delay, load_tables
tables = load_tables("delivery/batch_01")            # папка партии с CSV по контракту данных
score_delay(["UPD-0020874"], "2025-12-30", tables)
```

На выходе таблица: `upd_id`, `as_of_date`, `p_7`, `p_14`, `p_30`, `p_90`, `expected_days`, `model_version`, `status`. Статус `ok` или `no_history` (нет закрытых УПД ни у пары, ни у покупателя на дату `t`, вероятности пусты). Модель определена только для открытых УПД, срок оплаты которых не наступил (категории 1–4); для закрытых и просроченных функция выбрасывает `ValueError`.

## Подключение к сервису (ml-service-openapi.yaml)

Сервис ждёт модуль `app.models.delay_trained` с функцией `create()`, у модели — `version`, `trained_at`, `stub = False` и метод `score(request)`. Сейчас `score_delay` читает таблицы партии, а сервис получает JSON, поэтому нужен переходник.

Соответствие результата:

- `p_delay` = `p_<delay_threshold_days>` (порог из запроса: 7, 14 или 30);
- `p_overdue_90` = `p_90`;
- `expected_delay_days` = `expected_days`;
- статус `no_history` → `NO_PAYMENT_HISTORY` (вероятности не заполняются);
- `no_pair_history` = у пары нет закрытых УПД, а у покупателя есть (в таблице признаков `pair_n == 0` и `buy_n > 0`);
- закрытый или просроченный УПД: модель не определена, элемент отдаём со статусом `ERROR`.

Соответствие входа:

- УПД из `upds`: `client_inn` играет роль клиента, `upd_date` и `planned_due_date` — дата подписания и плановая дата оплаты, доля оплаты = `1 − outstanding / amount`, `client_industry` — отрасль клиента (допустимые значения в `model.industries`).
- `history`: оплаченные УПД (`PAID`, `paid_date` = дата закрытия) и открытые (`OPEN`, `outstanding`). Надёжнее всего собрать УПД и события оплат сразу из `history` и вызвать `dl_common.features`, не пересчитывая сверку оплат через `dl_common.reconcile`: так даты закрытия берутся ровно те, что прислал бэкенд.
- Покупатель: `pd` = `buyer_pd`; уровень A–D по порогам PD 0,4% / 1,5% / 6%; `payables_days` = 1520 / 2120 × 365; `abs_liquidity` = 1250 / 1500; `current_liquidity` = 1200 / 1500; `revenue_mln` = выручка (2110) в млн ₽; `age_years` = полных лет на конец года отчётности; `okved_section` и `region` как в контракте данных (регион латиницей по справочнику RFSD).

## Как проверить переходник

В каждой партии тестового набора лежит `delay_scores.csv` — эталонные оценки на 30.12.2025. Переходник на тех же данных должен дать те же числа: `p_*` с точностью до 6 знаков, `expected_days` до 2. Расхождения возможны только там, где сверка оплат на бэкенде отличается от правил приложения Б ТЗ.
